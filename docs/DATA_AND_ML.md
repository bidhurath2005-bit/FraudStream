# FraudStream — Data and machine learning

> **All performance numbers in this document are measured on synthetic data generated by FraudStream's own
> simulator.** They show that the pipeline learns the simulator's scenarios. They are **not** estimates of real-world
> fraud-detection performance.

Code: `simulator/`, `ml/` (datasets, features, preprocessing, training, evaluation, inference, explainability, drift),
`backend/app/risk_engine/`. Artifacts: `ml/artifacts/`. Dataset: `data/synthetic/`.

## 1. Synthetic dataset generation

`simulator/generator.py` (`TransactionGenerator`) produces events that follow the shared schema. Everything is
seeded, so the same configuration gives the same events.

- **Customer population:** each customer has a home city (one of **38 public city centroids** in
  `simulator/geography.py`), habitual devices, preferred merchant categories and a typical amount.
- **Normal behaviour:** Poisson arrivals at a configured rate, everyday categories (grocery, restaurants, fuel,
  utilities, retail, online services, entertainment, healthcare, electronics, travel), mostly the home city and known
  devices, a small rate of declined or failed authorisations.
- **Seven injected suspicious scenarios**, each a short burst of events over up to ~9 minutes:

| Scenario | Pattern |
|---|---|
| `large_amount` | amount far above the customer's history |
| `velocity_burst` | many transactions within a minute |
| `failed_attempts` | repeated declined/failed attempts, then a success |
| `account_takeover` | new device, new location, unusual spending |
| `impossible_travel` | a transaction from a distant city minutes after the previous one (the first, "anchor", event is labelled benign) |
| `odd_hour` | night-time spending far above the customer's mean |
| `suspicious_merchant` | first transaction in a high-risk category (gift cards, crypto exchange, gambling, money transfer) |

- **Labels:** each event carries `ground_truth = {is_suspicious, scenario}`. This is simulator metadata used **only
  for evaluation**.

### The training dataset

`data/synthetic/synthetic-fraudstream-v1.0.jsonl.gz` and its `.meta.json` (SHA-256
`b57801b3…5ba3e9`, recorded in the meta file and the experiment):

| Spec | Value |
|---|---|
| Customers | 3,000 |
| Duration / rate | 24 h from 2026-01-05 00:00 UTC at 1.5 events/s |
| Scenario injection | 1.5 % of customer activity (each scenario emits several events) |
| Seed | 2026 |
| **Rows** | **139,517** |
| **Labelled suspicious** | **7,064 (5.06 %)** |

`python -m ml.training.train` regenerates it deterministically if it is missing. Importers for two public datasets
(PaySim, IEEE-CIS) exist in `ml/datasets/public.py` and accept a user-supplied CSV through `--dataset paysim|ieee
--csv PATH`. **They were never used.** Nothing is downloaded, and the Kaggle sources require a login.

### Event schema (`streaming/schemas/events.py`, version 1.0)

| Field | Type / constraint |
|---|---|
| `event_id` | str 8–64 (dedup key) |
| `transaction_id`, `customer_id`, `account_id`, `merchant_id` | str 1–64 (`transaction_id` ≥ 4) |
| `merchant_name` | str ≤ 120 |
| `amount` | decimal > 0, ≤ 10,000,000, 2 decimals |
| `currency` | ISO-4217 code `^[A-Z]{3}$` |
| `event_time` | timezone-aware datetime |
| `transaction_type` | PURCHASE, TRANSFER, WITHDRAWAL, PAYMENT, REFUND |
| `merchant_category` | str |
| `channel` | CARD_PRESENT, ONLINE, MOBILE_APP, ATM, BANK_TRANSFER |
| `device_id`, `ip_address` | str |
| `location` | `{city, country (2 letters), lat, lon, simulated: true}` |
| `status` | APPROVED, DECLINED, FAILED |
| `schema_version`, `synthetic`, `source` | `"1.0"`, `true`, `simulator`/`api` |
| `ground_truth` | optional `{is_suspicious, scenario}`; **evaluation only** |

## 2. Feature engineering

`ml/features/definitions.py` (version **`fc-1.0`**) and `ml/features/engineering.py`. The same functions run in
training, in the local API pipeline, in Spark (`applyInPandasWithState` keeps a `CustomerState` per customer) and in
the fallback processor.

| Group | Features |
|---|---|
| Amount | `amount`, `log_amount`, `amount_zscore` (vs customer history, clipped ±50), `amount_to_mean_ratio` (clipped 0–1000) |
| Time | `hour_of_day`, `day_of_week` (UTC), `is_night` (00–05 h), `seconds_since_prev` (capped at 7 days) |
| Velocity | `tx_count_1m`, `tx_count_5m`, `tx_count_1h`, `spend_sum_15m`, `spend_sum_1h` |
| History | `hist_tx_count`, `hist_mean_amount`, `hist_std_amount` (Welford), `has_history` |
| Failures | `failed_count_1h`, `failed_ratio_hist` |
| Novelty | `is_new_device`, `is_new_location`, `is_new_merchant`, `merchant_frequency` |
| Geography | `geo_velocity_kmh` (great-circle distance from the previous event / elapsed time, min 1 minute) |
| Merchant risk | `is_high_risk_category` |
| Categorical (one-hot) | `merchant_category`, `channel`, `transaction_type`, `status` |

25 numeric + 4 categorical features. Every feature has a documented valid range (`FEATURE_RANGES`) that is checked
at inference. Per-customer state is bounded: 1 h of recent events (≤ 500), ≤ 20 devices, ≤ 30 locations, ≤ 200
merchants and ≤ 1,000 seen event ids. Changing any definition requires bumping `FEATURE_CONFIG_VERSION`, so models
trained on old definitions cannot be reused silently.

## 3. Leakage prevention

| Risk | Control |
|---|---|
| Labels or identifiers reaching the model | `FORBIDDEN_FEATURE_FIELDS` (`ground_truth`, `is_suspicious`, `scenario`, `label`, `is_fraud`, `event_id`, `transaction_id`); ground truth is stripped before feature computation; tests assert it |
| Using the current event in its own features | velocity and history features count **prior** events only (`[t − w, t]`, current event excluded) |
| Future information | features are computed in event-time order; the split is temporal |
| Same customer in train and test | 15 % of customers (deterministic SHA-256 hash with a salt) are removed from training and validation and form the **unseen-customer** test split |
| Choosing models or thresholds on test data | thresholds and the recommended model use the **validation** split only; test splits are reporting-only |

## 4. Train / validation / test strategy

`ml/preprocessing/splits.py` → `temporal_split()`:

1. Sort all events by `event_time`.
2. Cut at the 60 % and 80 % event-time quantiles → train / validation / test periods.
3. Remove held-out customers from train and validation. Their events after the validation cut form
   `unseen_customer_test`.

| Split | Rows | Positives | Period |
|---|---|---|---|
| train | 72,034 | 3,678 | ≤ 2026-01-05 14:27 UTC |
| validation | 24,079 | 1,158 | 14:27 – 19:12 UTC |
| test (temporal) | 24,155 | 1,211 | > 19:12 UTC, known customers |
| unseen-customer test | 3,749 | 203 | > 19:12 UTC, held-out customers |

Class imbalance in train: 18.6 negatives per positive. It is handled with `class_weight="balanced"` for logistic
regression, `balanced_subsample` for random forest, and `scale_pos_weight` for XGBoost.

## 5. Models and comparison

`ml/training/pipeline.py`: a scikit-learn `ColumnTransformer` (standardisation for the linear model, one-hot
encoding) plus the estimator. Baseline first: more complex models are preferred only if they beat logistic regression
on **validation** PR-AUC. Seed 7.

Experiment **`v20261114T124627Z`** (`ml/artifacts/experiments/v20261114T124627Z.json`), 72 s training time:

| Model | Kind | Validation PR-AUC | **Test** PR-AUC | Test precision | Test recall | Test F1 | Unseen-customer PR-AUC | Offline p50 latency (1 row) |
|---|---|---|---|---|---|---|---|---|
| Logistic regression | supervised (baseline) | 0.9776 | 0.9765 | 0.906 | 0.955 | 0.930 | 0.9711 | 9.2 ms |
| Random forest | supervised | 0.9978 | 0.9989 | 0.988 | 0.977 | 0.983 | 0.9982 | 27.5 ms |
| **XGBoost** (active) | supervised | **0.9990** | **0.9996** | **0.994** | **0.993** | **0.993** | 0.9990 | 8.3 ms |
| Isolation Forest (active anomaly) | unsupervised | 0.3165 | 0.3204 | 0.274 | 0.712 | 0.395 | 0.6045 | 24.3 ms |

**Selection rule** (stored in the experiment): *highest validation PR-AUC among supervised models; test set not
used* → XGBoost. PR-AUC is sklearn's step-wise average precision.

**How to read these numbers.** Scores this high mean the injected scenarios are close to separable in feature space
by construction. The simulator writes the patterns that the features were designed to detect. That validates the
pipeline wiring, the temporal split and the absence of leakage, but it does not show that the models would detect
real fraud. Real fraud is adversarial, labels arrive late and are noisy, and base rates are far below 5 %.

Explanations: `ml/explainability/contributions.py` computes per-prediction feature contributions from the fitted
model. XGBoost uses exact TreeSHAP (`pred_contribs`), logistic regression uses coefficient × standardised value, and
random forest uses Saabas path attribution (not Shapley). The Isolation Forest has none. The top contributions are
stored with each prediction and shown on the alert page.

## 6. Threshold selection

For each model, `choose_threshold()` picks the score that **maximises F1 on the validation split**
(`threshold_strategy="max_f1"`). The threshold is stored in the model metadata and `registry.json` (XGBoost: 0.847).
It is never tuned on test data.

The model threshold is not the alert threshold. The risk engine (§7) maps the model score so that the model's
threshold corresponds to 0.5 of the model component. The alert categories come from the risk score thresholds
(40 / 70).

## 7. Risk scoring (`backend/app/risk_engine/engine.py`, version `re-1.0`)

1. **Model component** `c_m = model_weight × n(s)`. Here `n` is piecewise-linear with `n(threshold) = 0.5`, `n(0) = 0`
   and `n(1) = 1`; the raw model score is not treated as a probability.
2. **Anomaly component** `c_a = anomaly_weight × max(0, (p − p_min) / (1 − p_min))`, where `p` is the Isolation
   Forest's training percentile. Only extreme anomalies contribute (`p_min = 0.97`).
3. **Rule components:** ten rules grouped into families. Only the strongest triggered rule per family counts, so
   correlated signals are not double-counted.

| Rule | Family | Weight | Default parameters |
|---|---|---|---|
| `LARGE_AMOUNT` | amount | 0.35 | absolute 5,000; ratio 8× mean; min_history 3 |
| `AMOUNT_DEVIATION` | amount | 0.30 | z-score 4.0; min_history 5 |
| `HIGH_VELOCITY_1M` | velocity | 0.35 | ≥ 4 prior in 60 s |
| `HIGH_VELOCITY_5M` | velocity | 0.30 | ≥ 8 prior in 5 min |
| `NEW_DEVICE_HIGH_SPEND` | device | 0.35 | ratio 3× mean |
| `IMPOSSIBLE_TRAVEL` | location | 0.45 | ≥ 900 km/h |
| `NEW_LOCATION` | location | 0.10 | — |
| `REPEATED_FAILURES` | failures | 0.35 | ≥ 3 failed in 1 h |
| `ODD_HOUR_HIGH_SPEND` | timing | 0.15 | 00–05 UTC and ratio 3× mean |
| `HIGH_RISK_MERCHANT_NEW` | merchant | 0.20 | — |

4. **Combination (noisy-OR):** `risk = 1 − Π(1 − c_i)`, `risk_score = 100 × risk`. This is a bounded, monotone
   heuristic, **not** a probability of fraud.
5. **Categories and actions:** LOW < 40 ≤ MEDIUM < 70 ≤ HIGH. LOW → ALLOW, MEDIUM → REVIEW, HIGH →
   BLOCK_SIMULATION (or REVIEW if that flag is off). Nothing real is blocked. `detection_method` is ML, ANOMALY, RULES,
   HYBRID (more than one source) or NONE.

Defaults: `model_weight 0.90`, `anomaly_weight 0.30`, `anomaly_min_percentile 0.97`, thresholds 40 / 70. All of these
values and every rule can be changed by an admin (validated, versioned, audited — see
[API_DOCUMENTATION.md §9](API_DOCUMENTATION.md#9-risk-configuration-and-settings-optimistic-concurrency)). Changes apply
to new transactions only.

## 8. Inference architecture

- `ml/inference/scorer.py` loads the **active** supervised and anomaly models named in `registry.json` from
  `ml/artifacts/models/<model>/<version>/model.joblib`, checks the feature-config version and raises
  `ModelUnavailableError` rather than inventing a score.
- `ml/inference/fast_transform.py` re-implements the fitted preprocessing and Isolation Forest scoring with NumPy for
  single events (tested to match the scikit-learn pipeline). In live traffic, measured inference takes a few
  milliseconds per event; `GET /models/live-inference` reports p50/p95/p99 from persisted `predictions.inference_ms`.
- **Where inference runs:**
  - *Distributed:* inside Spark's Python workers. A custom daemon loads the models once before forking, and the
    artifacts are mounted read-only.
  - *Local:* inside the API process.
  - The fallback processor uses the same scorer.
- The ML libraries are pinned identically in the API and Spark images (scikit-learn 1.5.2, XGBoost 2.1.3, NumPy
  2.1.3, pandas 2.2.3, joblib 1.4.2) because joblib artifacts are version-sensitive.
- **Registry:** `ml/artifacts/registry.json` is the source of the active versions. At start-up the API syncs it into
  the `model_versions` table. Activation and rollback endpoints exist, are admin-only and audited, and return **409
  while `ml/artifacts` is mounted read-only** (the default).

## 9. Drift monitoring

`ml/drift/psi.py`. At training time each model stores a `reference_profile.json`: decile bins for numeric features,
category proportions for categorical features, and the score distribution.

`GET /drift/current` (the "Run drift check now" button on Model Intelligence → Drift):

1. takes the most recent `window_rows` (default 2,000) predictions of the active supervised model;
2. computes the **Population Stability Index** per feature and for the model score against the reference,
   `PSI = Σ (cur − ref) · ln(cur / ref)`, with bins fixed on the reference;
3. classifies with configurable thresholds: < 0.10 stable, 0.10–0.25 moderate, ≥ 0.25 significant (`INSUFFICIENT_DATA`
   below `min_rows`, default 200);
4. adds labelled precision and recall on those rows against **simulator ground truth**, next to the test metrics;
5. stores the report (`drift_reports`) unless `persist=false`.

There is no scheduled drift job; checks run on demand.

**Current reading:** drift is SIGNIFICANT (e.g. `hour_of_day` PSI 8.29, model-score PSI 0.75). Live simulator traffic
is stamped near "now" and starts with short customer histories, while the training set covers one simulated day with
full histories. Labelled live precision/recall were 0.964 / 0.924 against test 0.994 / 0.993.

## 10. Research limitations

- **Synthetic only.** Both the scenarios and the features come from the same author. High separability is expected
  and is not evidence of real-world efficacy. No public dataset was evaluated.
- **Label quality.** Simulator labels are exact and immediate. Real labels (chargebacks, analyst decisions) are
  delayed, incomplete and noisy. The analyst decisions captured in the UI are not fed back into training.
- **One training run.** One dataset, one seed, one experiment. No confidence intervals, cross-validation or
  hyperparameter search are reported.
- **Base rate.** 5.06 % positives is far higher than typical fraud rates, which flatters precision.
- **Threshold choice.** Max-F1 treats false positives and false negatives as equally costly. No cost-sensitive
  analysis was done.
- **PSI** detects input distribution change only. It does not establish concept drift, and the current SIGNIFICANT
  reading mainly reflects the difference between simulated live timing and the training day.
- **Geography** is a set of 38 public city centroids, not addresses. Geo-velocity is computed between centroids.
- **No retraining loop.** Retraining is manual (`python -m ml.training.train`) and produces new artifacts.
  Activation is disabled while artifacts are read-only.
