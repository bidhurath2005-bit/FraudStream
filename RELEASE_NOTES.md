# FraudStream 1.0.0 — Release notes

_Source release, 2026-11-16. Distributed as `FraudStream.zip` with a separate `FraudStream.zip.sha256`._

> **Educational project, synthetic data only.** Every transaction, customer, merchant and location is generated by
> the built-in simulator. Risk scores are model estimates, not determinations of fraud, and nothing real is ever
> blocked. FraudStream has **not** been deployed to production. All performance figures come from **one development
> machine** and are not production capacity. The model metrics are measured on synthetic data and say nothing about
> real-world fraud detection.

## 1. What FraudStream is

A real-time fraud-detection platform for synthetic payment transactions. A simulator produces events into Kafka.
Spark Structured Streaming validates and deduplicates them, computes per-customer behavioural features, and scores
them with an XGBoost model, an Isolation Forest and an explainable rule engine. A persistence consumer writes the
results to PostgreSQL, and a React dashboard gives analysts live monitoring, alert triage, investigations, analytics
and reports. A lighter **local profile** runs the same scoring in-process on SQLite, without Kafka or Spark.

## 2. Main capabilities

- **Streaming pipeline**: 7 Kafka topics, idempotent producers, 6 Spark queries (scoring with RocksDB state, watermark
  deduplication, tumbling and sliding windows), checkpoints, an idempotent persistence consumer with a dead-letter
  topic.
- **Scoring**: 29 versioned features; XGBoost (supervised) + Isolation Forest (anomaly); 10 rules in 7 signal
  families combined with noisy-OR; thresholds 40 / 70; actions ALLOW / REVIEW / BLOCK_SIMULATION (simulation only).
- **Analyst workflow**: live SSE feed, alerts, assignment, notes, investigations with final classification, CSV export,
  per-alert audit history.
- **Dashboards**: Intelligence Overview, Live Stream, Investigation Center, Simulation Lab (7 injectable scenarios),
  Streaming Infrastructure, Model Intelligence (registry, comparison, drift), Risk Analytics, Fraud Intelligence Map,
  Reports (6 types, CSV and PDF), Settings (validated, audited, optimistic concurrency). Usable at 390 px width.
- **Security**: Argon2id passwords, short-lived HS256 access tokens, rotating refresh tokens with reuse detection,
  server-side RBAC (ANALYST / ADMIN), login and API rate limits, strict input validation, complete audit trail,
  non-root containers, every host port bound to 127.0.0.1.
- **Operations**: health checks and memory limits on every service, snapshot-consistent backup, restore into empty
  targets only, and automated restore verification.
- **Automation**: GitHub Actions workflows (`ci.yml` per PR, `full-stack.yml` weekly or manual) with repository
  hygiene, gitleaks, pip-audit / npm audit gated on a reviewed baseline, and Trivy.

## 5. Measured performance (Phase 12, one machine)

Windows 11, Intel Core 7 240H (16 logical CPUs), Docker Desktop VM with 7.6 GiB; Spark in local mode with a 3 GiB
limit. Details: [docs/phase12/RELIABILITY_REPORT.md](docs/phase12/RELIABILITY_REPORT.md).

| Measurement | Result |
|---|---|
| End-to-end latency, Kafka → Spark → PostgreSQL | p50 / p95 **2.5 / 3.4 s** at 10 ev/s; **3.8 / 5.6 s** at 100 ev/s |
| Sustained throughput | **≈ 100–105 ev/s** persisted; above that the backlog grows |
| Backlog burst of 5,000 events | one 14.7 s Spark micro-batch (≈ 340 ev/s); persistence at 217 ev/s |
| Correctness under load | 0 lost, 0 duplicate rows, 0 dead letters in every run |
| HTTP ingestion (one API process) | ≈ 65 accepted ev/s |
| Reports | each type ≤ 2.3 s, PDF ≤ 2.5 s on ~190k transactions |

## 6. Reliability and restoration evidence

- Kafka stopped for 20 s during production: every acknowledged event persisted exactly once; lag back to 0 within
  49–56 s of the restart.
- Spark stopped while 3,000 events arrived: drained from its checkpoint exactly once in 53–78 s.
- Redis outage: persistence continued; the live feed recovered 16–21 s after Redis returned.
- Full stack stop and start: healthy in 22–45 s with all data intact.
- Backup → restore into a separate stack: row counts, 16 table content fingerprints, model and dataset SHA-256,
  Kafka offsets and Spark checkpoints identical; `verify_restore.py` 10/10. Repeated in Phases 14 and 15
  ([DEVELOPMENT_STATUS.md](DEVELOPMENT_STATUS.md)).

## 7. Security in this release

Phase 15 upgraded the dependencies with known advisories. **105 of 123** reviewed advisories are fixed, including all
17 for PyJWT. Two of those PyJWT issues were reachable in FraudStream's token check (`crit` header, signature
malleability); new tests prove they failed on the old version and pass now. The frontend image moved to nginx 1.30.6
on Alpine 3.24 and has **0** HIGH/CRITICAL OS findings (68 before). The **18** remaining advisories are classified in
[SECURITY.md §10](SECURITY.md#10-dependency-findings-reviewed-2026-11-16-phase-15): pyarrow inside the Spark image
(code path not used), two react-router issues that need 7.x (mitigated in the app / SSR only) and Vite/Vitest
development tooling.

## 8. Getting started

Requirements: Docker Desktop with Compose v2 (Docker VM **≥ 8 GB RAM** for the distributed profile), Python 3.12,
Node.js 22+ (tests and development only). About 7 GB of disk for the images.

```powershell
# from the extracted FraudStream folder (Windows PowerShell; on Linux/macOS use .venv/bin/python)
python -m venv .venv
.\.venv\Scripts\python -m pip install -r backend\requirements-dev.txt
.\.venv\Scripts\python scripts\new_env.py                       # .env with fresh random secrets and passwords

# full platform: Kafka, Spark, PostgreSQL, Redis, API, dashboard -> http://127.0.0.1:8080
docker compose --env-file .env --profile distributed up -d --build

# or the light local profile (SQLite, in-process scoring)      -> http://127.0.0.1:8081
docker compose --env-file .env --profile local up -d --build api-local frontend-local
```

Log in with `FRAUDSTREAM_ANALYST_USERNAME` / `FRAUDSTREAM_ANALYST_PASSWORD` (or the admin pair) from your `.env`.
Stop with `docker compose --env-file .env --profile distributed stop`; this keeps all data. **`down -v` deletes all
data.** The compose file pins the project name `fraudstream`: to run a second copy next to an existing installation,
use `-p <other-name>` with `infrastructure/isolated/docker-compose.isolated.yml` and a separate env file (see
[CONTRIBUTING.md](CONTRIBUTING.md)). Full instructions: [README.md §5](README.md#5-installation-and-execution);
demonstration script: [docs/DEMO_GUIDE.md](docs/DEMO_GUIDE.md).

The archive contains the trained model artifacts (`ml/artifacts/`) and the synthetic dataset (`data/synthetic/`).
Do not retrain unless you mean to: retraining produces different model files.

## 9. Known limitations

- Single host: one Kafka broker (RF=1), one PostgreSQL, one Redis; Spark in local mode in one container. No high
  availability; Docker restart policies give process-level recovery only.
- No TLS anywhere; Kafka has no authentication. Run it on 127.0.0.1 only, as configured.
- Sustained capacity on the test machine is ≈ 100–105 ev/s; one API process accepts ≈ 65 ingested ev/s.
- Models are trained and evaluated on simulator data; their metrics (test PR-AUC 0.9996) are optimistic and do not
  reflect real-world fraud.
- Drift against the training profile reads SIGNIFICANT for live simulator traffic, which is expected and measured.
- The CI workflows have been run locally and step by step, but **not yet on GitHub**.
- Remaining dependency advisories and their plan: [SECURITY.md §10.2](SECURITY.md#102-remaining-18-advisories-in-the-baseline).
- More: [DEVELOPMENT_STATUS.md §8](DEVELOPMENT_STATUS.md#8-known-limitations), [SECURITY.md §11](SECURITY.md#11-known-limitations-not-fixed).
